Error Handling

Exceptions → structured JSON via RFC 9457 Problem Details.

Key Points

  • Every error returns RFC 9457 Problem Details — structured JSON, not plain text
  • A single ExceptionTranslator (@RestControllerAdvice) handles all exceptions globally
  • Domain exceptions map to specific HTTP statuses; unexpected errors become 500
  • Dev profile includes exception class name and stackTrace; production omits them
  • Every error response includes a timestamp and request metadata for correlation

Problem Details Format

Every error response body follows the RFC 9457 structure plus custom extensions:

{
  "type": "https://api.boot4ref.example.com/errors/404",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "Product not found with id: 553726781652992",
  "instance": "/api/products/553726781652992",
  "errorCode": "RESOURCE_NOT_FOUND",
  "timestamp": "2026-03-01T12:00:00Z",
  "request": {
    "httpMethod": "GET",
    "requestPath": "/api/products/553726781652992"
  }
}
FieldSourcePurpose
typeBase URL + status codeMachine-readable error type URI
titleHTTP status reason phraseHuman-readable summary
statusHTTP status codeRedundant but useful when body is logged separately
detailException messageSpecific description of what went wrong
instanceRequest URIWhich resource was affected
errorCodeCustom extensionApplication-level code for client error handling
timestampCustom extensionWhen the error occurred (ISO-8601 UTC)
requestCustom extensionHTTP method + path for log correlation

  RuntimeException
  ├── ResourceNotFoundException          → 404

  // Domain-specific subclasses:
  ResourceNotFoundException
  ├── ProductNotFoundException
  └── OrderNotFoundException

  ResourceConflictException
  ├── ProductConflictException

Domain packages define specific subclasses (e.g., ProductNotFoundException extends ResourceNotFoundException). The ExceptionTranslator catches the base types, so subclasses are handled automatically.

ExceptionTranslator Code Trace

File: common/rest/ExceptionTranslator.java

@RestControllerAdvice with @Order(Ordered.HIGHEST_PRECEDENCE) — runs before Spring's defaults. Each exception type has a dedicated @ExceptionHandler method.

All handlers delegate to buildErrorResponse():

  1. Creates a ProblemDetail instance with status, title, and detail
  2. Sets type to https://api.boot4ref.example.com/errors/{status}
  3. Sets instance to the request URI
  4. Adds custom properties: errorCode, timestamp, request metadata
  5. In dev profile: adds exception (class name) and stackTrace
  6. Logs the error at appropriate level (WARN for 4xx, ERROR for 5xx)
  7. Returns ResponseEntity<ProblemDetail>

Validation errors get special treatment

For MethodArgumentNotValidException (bean validation failures), the translator extracts individual field errors and includes them as an errors array in the response:

{
  "status": 400,
  "title": "Validation Error",
  "detail": "Validation failed for object='createProductRequest'. Error count: 2",
  "errors": [
    { "field": "name", "message": "size must be between 3 and 100", "rejectedValue": "ab", "errorCode": "Size" },
    { "field": "price", "message": "must be positive", "rejectedValue": "-1", "errorCode": "Positive" }
  ]
}

Dev vs Production

The translator checks env.acceptsProfiles(Profiles.of("dev")). Dev gets stack traces for debugging. Production doesn't leak internals.

Trace IDs and Observability

With the observability stack running (OTel Collector + Grafana), every request gets a trace ID via MDC. Error log entries include this trace ID, so:

  1. See the error in application logs (Loki)
  2. Click the trace ID to jump to the full distributed trace (Tempo)
  3. See request latency and error rate metrics (Prometheus)

The MDC pattern %X{traceId} puts trace IDs in every log line. See Observability for the full pipeline.

Adding New Exceptions

  1. Create the exception class in the appropriate domain exception/ package, extending one of the base types (ResourceNotFoundException, ResourceConflictException, BusinessRuleException)
  2. Throw it from the service layer
  3. That's it — ExceptionTranslator already handles the base type

For a new base exception type with a different HTTP status:

  1. Create the exception in common/exception/
  2. Add an @ExceptionHandler method in ExceptionTranslator
  3. Add tests in ExceptionTranslatorTest

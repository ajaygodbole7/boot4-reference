## 2. RFC 9457 Violations: Verified Against Code

### Violation 1: `type` URI uses status code (CONFIRMED)

**Spec claim:** `type` URI is `errorBaseUrl + status.value()`, making it identical to `status`.

**Actual code (`ExceptionTranslator.java` line 279):**
```java
problemDetail.setType(URI.create(errorBaseUrl + status.value()));
```

**Verdict:** Correct. Three 409 exceptions (`ResourceConflictException`, `ConcurrencyFailureException`, `DataIntegrityViolationException`) produce identical `type` URIs. This violates RFC 9457 section 3.1 which states `type` MUST identify the problem type.

### Violation 2: `type` URIs not dereferenceable (CONFIRMED)

Spec correctly identifies this as SHOULD-level (not MUST). The proposed slug-based URIs still aren't dereferenceable but are semantically meaningful. Acceptable pragmatic position.

### Violation 3: `errorCode` duplicates `type`'s role (CONFIRMED)

**Actual code (line 281):**
```java
problemDetail.setProperty(ERROR_CODE, title.toUpperCase().replace(" ", "_"));
```

**Verdict:** Correct. `errorCode` derived from title is fragile (title renames silently break clients). Slug-derived `errorCode` is a clean fix.

| **F2** | **Annotating abstract `BusinessRuleException` is dead code** | `@ProblemType` on abstract `BusinessRuleException` is never read because `ex.getClass()` always returns a concrete subclass. Without `@Inherited`, the annotation on the base class has no effect. Either: (a) add `@Inherited` to `@ProblemType`, (b) remove the annotation from `BusinessRuleException`, or (c) document this as intentional (fallback test already covers the behavior). A `@ProblemType(status=500)` on a `ResourceNotFoundException` subclass would silently return 500 from the 404 handler. Need either: (a) validation that annotation status matches handler default, (b) ignore annotation status (only use slug/title), or (c) document as intentional escape hatch. |

## 5. Developer Feedback Review (5 items)

### Item 1: Task 5 / Task 10 collision on `handleServiceUnavailable`

**Feedback:** Both rewrite `handleServiceUnavailable` differently. Task 5 uses `buildErrorResponse`, Task 10 replaces with `buildDomainErrorResponse`. Add a forward reference or merge.

**Verdict: VALID.** Verified against spec:
- Task 5 (lines 285-290) rewrites to: `buildErrorResponse(...)` then re-wraps with `Retry-After`
- Task 10 (lines 598-607) rewrites to: `buildDomainErrorResponse(...)` then re-wraps with `Retry-After`

The implementer writes this method twice. Task 5's version is dead code the moment Task 10 lands. The spec should either add a forward reference in Task 5 ("Note: Task 10 will replace this with `buildDomainErrorResponse`") or merge the `Retry-After` addition into Task 10 directly.

**Severity: Medium.** Not a correctness issue but creates confusion for the implementer.

### Item 2: Same collision for `handleTransientDataAccess`

**Feedback:** Task 5 inlines ProblemDetail construction for `Retry-After`. Task 10 says infrastructure handlers "keep their hardcoded slugs" without confirming Task 5's form is preserved.

**Verdict: VALID.** Verified:
- Task 5 (lines 292-299) inlines `createBaseProblemDetail(...)` + `pd.setDetail(...)` + `Retry-After` header
- Task 10 (line 611) says "Infrastructure handlers (`handleConcurrencyFailure`, `handleDataIntegrityViolation`, `handleTransientDataAccess`, catch-all) keep their hardcoded slugs — no annotation needed."

Task 10 does NOT show the code for `handleTransientDataAccess` — it only confirms it keeps hardcoded slugs. The implementer must infer that Task 5's inlined form is preserved. The spec should explicitly confirm Task 5's `handleTransientDataAccess` code is the final form.

**Severity: Medium.** Ambiguity risk.

### Item 3: Shared `validation-error` slug

**Feedback:** `handleValidationException` produces `$.errors[]`, `handleMethodValidation` produces `$.validationErrors[]`. Different payloads, same `type` URI. Either split the slug or add a rationale.

**Verdict: VALID.** Matches code review finding S1. The spec slug mapping table shows both handlers producing `.../errors/validation-error`. Clients cannot distinguish the two problem types by `type` URI alone — they must inspect the response body structure. This partially contradicts the stated goal of "every handler produces a unique `type` URI" (success criterion 1).

Options:
- Split: `request-body-validation-error` / `parameter-validation-error`
- Keep shared slug with explicit rationale: "Both represent validation failures; the response structure (`errors[]` vs `validationErrors[]`) provides discrimination."

**Severity: Low-Medium.** Not a bug, but a conscious trade-off that should be documented either way.

### Item 4: Content-Type never set to `application/problem+json`

**Feedback:** Not in current code, not in the spec. Add `.contentType(MediaType.APPLICATION_PROBLEM_JSON)` to response builders.

**Verdict: VALID.** Current code:

```java
// buildErrorResponse (line 263):
return ResponseEntity.status(status).body(problemDetail);
```

No explicit `.contentType(MediaType.APPLICATION_PROBLEM_JSON)`. Spring Boot 4 with `spring.mvc.problemdetails.enabled=true` configures `ProblemDetailReturnValueHandler` which may auto-negotiate `application/problem+json`. However, the `@RestControllerAdvice` with `@Order(HIGHEST_PRECEDENCE)` bypasses the normal `ProblemDetailsExceptionHandler` flow. Whether `application/problem+json` is set depends on Spring's content negotiation for `ProblemDetail` return types in the `@RestControllerAdvice` path.

**Recommendation:** Explicitly set `.contentType(MediaType.APPLICATION_PROBLEM_JSON)` in `buildErrorResponse` and `buildDomainErrorResponse`. This guarantees RFC 9457 compliance regardless of content negotiation behavior.

**Severity: Medium.** Potentially a real RFC 9457 compliance gap.

### Item 5: Success criterion #8 says "10 domain exception classes"

**Feedback:** Actual count is 11. Fix the number.

**Verdict: VALID.** Duplicate of code review finding F1. The spec itself says "That's 11 classes total (4 base + 7 leaf)" at line 635. Success criterion 8 should say 11.

**Severity: Low.** Cosmetic but creates confusion.

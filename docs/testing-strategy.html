Testing Strategy

Unit tests (Surefire) and integration tests (Failsafe) across the full domain.

Key Points

  • Unit tests (*Test.java) run with Maven Surefire — fast, no containers
  • Integration tests (*IT.java) run with Maven Failsafe — real PostgreSQL via Testcontainers
  • mvn verify runs both. mvn test runs unit tests only
  • Controller tests use @WebMvcTest (Boot 4 package), service tests use Mockito, repository tests use Testcontainers
  • datasource-proxy wraps the DataSource in ITs to assert exact SQL query counts (N+1 detection)

Testing Pyramid

           ┌─────────┐
           │  E2E    │  infra/e2e-test.sh (shell, against running stack)
          ─┼─────────┼─
         / │  Integ  │ \  ITs — real DB, Testcontainers, concurrency
        /  ─┼─────────┼─  \
       /  / │  Unit   │ \  \  Mockito, @WebMvcTest, pure logic
      ────────────────────────

Bottom-heavy by design:

  • Unit — fast (seconds), catches most logic bugs
  • Integration — real database, concurrency, Testcontainers
  • E2E — shell script (infra/e2e-test.sh) against the full Docker stack

Deep Dive: Unit Tests

Service Tests

Pattern: @ExtendWith(MockitoExtension.class) with @Mock and manual constructor injection via factory methods.

Examples: ProductServiceTest, OrderServiceTest, OutboxWriterTest

Repository layer is mocked. Tests check:

  • Happy-path return values
  • Correct exceptions on error cases
  • Dependency interactions (verify(repository).save(...))
  • Lifecycle state transitions — valid and invalid

Entity and Enum Tests

Examples: OrderStatusTest, OrderTest, AbstractAuditingEntityTest, ProductFixturesTest

Pure Java logic — status transitions, bidirectional sync methods, equals/hashCode contracts, fixture generation.

Deep Dive: Controller Tests

Pattern: @WebMvcTest(ProductController.class) — loads only the web layer, not the full context.

Import: org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest (Boot 4 modular package)

Examples: ProductControllerTest, OrderControllerTest

MockMvc + @MockitoBean on the service layer. No database, no Testcontainers.

Checks:

  • HTTP status codes per endpoint
  • JSON response structure and field values
  • Bean validation (empty body, missing fields, invalid values → 400)
  • Content-Type enforcement (PATCH requires application/json)
  • Location header on 201 responses

Deep Dive: Repository Tests

Pattern: @SpringBootTest + Testcontainers PostgreSQL

Examples: ProductRepositoryIT, OrderRepositoryIT, FlywayMigrationIT

Repository ITs verify:

  • Flyway migrations apply cleanly to a real PostgreSQL instance
  • Keyset pagination queries return correct results with cursors
  • Filtering by status, price range works correctly
  • JOIN FETCH queries load associations without N+1
  • Hibernate batch inserts/updates work as configured

Deep Dive: Full-Stack Integration Tests

Pattern: @SpringBootTest with full application context + Testcontainers

Examples: OutboxIT, Boot4RefApplicationIT

Full service → repository → database path with real transactions. ACID properties, cascade behavior, outbox end-to-end.

Deep Dive: Concurrency Tests

File: OrderServiceConcurrencyIT

Concurrency tests use ExecutorService with multiple threads to verify:

  • Pessimistic lock correctness: concurrent order placement for the same product must not oversell stock
  • Optimistic lock retry: concurrent status transitions on the same order — one succeeds, the other retries via @Retryable
  • Stock consistency: after N concurrent orders, the total stock decrement equals the sum of successful orders
Why concurrency tests matter: Stock is a classic race condition. Without pessimistic locking, two concurrent orders both read stock=10, both pass validation, both decrement to 8 — overselling by 2. The concurrency ITs catch this.

Deep Dive: Query Count Assertions

File: DataSourceProxyConfiguration (test scope)

datasource-proxy wraps the JDBC DataSource and counts SQL statements. N+1 problems get caught in tests, not production.

How it works:

  1. DataSourceProxyConfiguration wraps the real DataSource with a ProxyDataSource
  2. A QueryCountHolder tracks SELECT/INSERT/UPDATE/DELETE counts per thread
  3. Tests reset the counter, perform an operation, then assert the exact query count
// Example from OrderRepositoryIT: verify JOIN FETCH is exactly 1 query
QueryCountHolder.clear();
Order found = orderRepository.findByIdWithLines(saved.getId()).orElseThrow();
assertThat(found.getOrderLines()).hasSize(1);
long selectCount = QueryCountHolder.getGrandTotal().getSelect();
assertThat(selectCount)
        .as("findByIdWithLines should execute exactly 1 SELECT (JOIN FETCH)")
        .isEqualTo(1);

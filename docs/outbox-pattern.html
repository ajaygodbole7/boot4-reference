Transactional Outbox Pattern

How domain state changes and event publishing stay atomically consistent — no dual writes, no lost events.

Key Points

  • The dual-write problem: writing to the DB and publishing to Kafka cannot both succeed atomically without coordination
  • The outbox solution: write the event to the same database in the same transaction as the domain change — ACID guarantees atomicity
  • A SKIP LOCKED poller reads committed outbox rows and publishes to Kafka (eventually consistent delivery)
  • Events use CloudEvents 1.0 format via the native Java SDK
  • The event hierarchy is a sealed interface — adding a new event type without handling it is a compile error

The Problem

When an order is created or transitioned, two things must happen atomically:

  1. The domain state changes (INSERT/UPDATE in orders, order_lines, products)
  2. An event record is written so downstream consumers eventually learn about the change

Publishing directly to Kafka inside the transaction is a dual write — if the Kafka send succeeds but the DB commit fails (or vice versa), the systems diverge. In financial systems where money is involved, this is unacceptable.

The Solution: Single-Writer Transactional Outbox

Both the domain write and the event write target the same database in the same transaction. The database — not the application, not a framework, not an in-memory bus — guarantees ACID atomicity.

@Transactional
public OrderResponse create(OrderCreateRequest request, String idempotencyKey) {
    // 1. Domain writes: order, order_lines, product stock decrement
    Order saved = orderRepository.save(order);

    // 2. Outbox write: same transaction, same database
    outboxPublisher.publish(new DomainEvent.OrderPlaced(
            saved.getId(), Instant.now(), saved.getTotalAmount(),
            saved.getOrderLines().size()));

    // 3. Commit: both succeed or both roll back. Zero window of inconsistency.
    return toResponse(saved);
}

A separate OutboxPoller (SKIP LOCKED) reads committed outbox rows and publishes to Kafka. This is eventually consistent delivery, but the outbox row is immediately consistent with the domain state.

Why Not Framework Abstractions?

The crash test: what happens when the container is killed mid-operation? With our approach, the answer is always the same: if the database committed, both the order and the outbox row are durable. If not, neither exists. There is no in-memory state, no framework queue, no "hope the framework flushes before the kill signal arrives."

Framework-based approaches (Spring Modulith, AOP aspects) introduce indirection between the domain operation and the outbox write. This indirection creates a window of vulnerability:

  • The domain operation commits
  • The framework intends to persist the event
  • The JVM crashes, the container is killed, the pod is evicted
  • The event is lost

In a system that processes payments, lost events mean lost money, phantom orders, or customers charged without fulfillment. The explicit same-transaction insert eliminates this window entirely.

Why the Coupling Is Intentional

"Every order state change MUST produce an event" is a business requirement, not a cross-cutting concern. It belongs in the service method, visible to every developer who reads the code, visible in every code review. Making it explicit means:

  • Anyone reading OrderService.create() sees the outbox call and understands: "this operation produces an event"
  • A code reviewer can verify: "yes, every write path includes an outbox publish"
  • Removing the outbox call is a conscious, reviewable decision — not an accidental side effect of refactoring an aspect pointcut

Architecture

Key Components

  • OutboxPublisher (outbox/OutboxPublisher.java) — Builds CloudEvents 1.0 payload (native SDK), inserts into outbox_events. No @Transactional of its own — inherits the caller's transaction
  • OutboxPoller (outbox/OutboxPoller.java) — @Scheduled every 1 second. SELECT ... FOR UPDATE SKIP LOCKED ensures parallel pollers claim different rows
  • KafkaEventPublisher (outbox/KafkaEventPublisher.java) — Extracted as separate @Component so @Retryable fires through AOP proxy. 3 attempts with exponential backoff and jitter (delay=200ms, multiplier=2). On failure after retries, the exception propagates to the poller which increments retryCount; after maxRetryCount (default 5) poll-cycle failures, the event is marked FAILED
  • Cleanup job — Deletes PROCESSED entries older than app.outbox.retention-days (default 7) every app.outbox.cleanup-interval-ms (default 1 hour)

SKIP LOCKED Explained

The poller query uses SELECT ... FOR UPDATE SKIP LOCKED. This PostgreSQL feature means:

  • Rows locked by another transaction are skipped, not blocked on
  • Multiple poller instances can run concurrently without contention
  • If a poller crashes, its locks are released automatically — rows become available on the next poll

Sealed Event Hierarchy

public sealed interface DomainEvent {
    Long orderId();
    Instant timestamp();

    record OrderPlaced(Long orderId, Instant timestamp,
                       BigDecimal totalAmount, int lineCount) implements DomainEvent {}
    record OrderConfirmed(Long orderId, Instant timestamp) implements DomainEvent {}
    record OrderShipped(Long orderId, Instant timestamp)   implements DomainEvent {}
    record OrderDelivered(Long orderId, Instant timestamp) implements DomainEvent {}
    record OrderCancelled(Long orderId, Instant timestamp) implements DomainEvent {}
}

The sealed keyword means adding a new event type without handling it in OutboxPublisher.resolveEventType() is a compile error. No event can be silently dropped.

Failure Modes

ScenarioOutcome
JVM crash before commitBoth domain write and outbox write roll back. No inconsistency.
JVM crash after commitBoth durable. Poller picks up the outbox row on next cycle.
Kafka down@Retryable retries 3 times with exponential backoff + jitter. If still down, the poller increments the event's retryCount and continues to the next event in the batch. After maxRetryCount (default 5) poll-cycle failures, the event is marked FAILED. The outbox table IS the retry buffer — events accumulate as PENDING rows and drain automatically when Kafka recovers. No manual intervention needed.
Poller crash mid-batchSKIP LOCKED rows revert to PENDING (lock released on disconnect). Next poll picks them up.
Duplicate deliveryPossible (at-least-once). Consumers must be idempotent. CloudEvents id field enables deduplication.

Design Decision: Single Transaction for Poll + Publish

The poll() method holds a DB connection and row locks for the entire batch — including Kafka network I/O. With 50 events and a healthy Kafka (10ms per send), that's ~500ms of connection hold time. This is a deliberate trade-off for simplicity:

  • Three states: PENDING, PROCESSED, and FAILED. No transient IN_PROGRESS state, no stale-event sweeper, no partial-batch orphan recovery. Events that exceed maxRetryCount are marked FAILED and excluded from future polls.
  • Crash at any point = consistent: before commit → TX rollback → all events revert. After commit → events are PROCESSED or have updated retry counts. No window of ambiguity.
  • Continue-on-failure: a Kafka failure on one event does not abort the batch. The poller increments retryCount, logs a warning, and moves to the next event. This prevents one poison-pill event from blocking the entire batch.
Scaling beyond this design At high throughput (thousands of events/sec) or with tight HikariCP pool sizing, the connection hold time becomes a bottleneck. The next step is splitting into Tx1 (claim rows → IN_PROGRESS) and Tx2 (mark PROCESSED after Kafka ACK) — but this requires a stale-event reaper for crash recovery and careful handling of partial batches. At that scale, consider Debezium CDC instead, which eliminates application-level polling entirely.

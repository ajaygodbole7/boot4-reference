Request Lifecycle

An HTTP request traced through every layer, from dispatch to database commit.

Key Points

  • Every request follows: Controller → Service → Repository → Database → Response
  • Controllers implement an Api interface (annotations) and delegate all logic to the service
  • Services own @Transactional boundaries — controllers never manage transactions
  • Bean validation fires automatically on @Valid request bodies before the controller method executes
  • Any exception is caught by ExceptionTranslator and converted to RFC 9457 Problem Details

Deep Dive: Tracing POST /api/orders

Order creation is the most complex request in the system. It hits every pattern: validation, locking, stock management, outbox events, idempotency.

HTTP 1. Controller Layer

File: order/rest/OrderController.java

OrderController.createOrder() implements OrderApi (endpoint mappings + OpenAPI annotations). Zero business logic here:

@Override
public ResponseEntity<OrderResponse> createOrder(
        @Nullable String idempotencyKey,
        OrderCreateRequest request) {
    OrderResponse created = orderService.create(request, idempotencyKey);
    URI location = URI.create("/api/orders/" + created.id());
    return ResponseEntity.created(location).body(created);
}

Spring's DispatcherServlet has already:

  • Deserialized the JSON body into OrderCreateRequest (Jackson 3)
  • Run @Valid bean validation — if items is empty or quantity is null, a MethodArgumentNotValidException is thrown and caught by ExceptionTranslator → 400
  • Extracted the Idempotency-Key header into the idempotencyKey parameter

SERVICE 2. Service Layer

File: order/service/OrderService.java

The create() method is @Transactional. Everything from here until the method returns is a single database transaction.

First, the idempotency check: if a non-null idempotencyKey was provided and an order already exists with that key, the existing order is returned immediately. No duplicate is created.

REPO 3. Pessimistic Locking

File: product/repository/ProductRepository.java

Product IDs from the request are sorted before locking. This prevents deadlocks when concurrent orders reference the same products in different order.

SELECT p FROM Product p WHERE p.id IN :ids ORDER BY p.id
-- with @Lock(LockModeType.PESSIMISTIC_WRITE)

The SELECT ... FOR UPDATE blocks other transactions from modifying these rows until our transaction commits.

SERVICE 4. Business Validation

With locks held, the service validates each line item:

  • Product must exist (otherwise ProductNotFoundException → 404)
  • Product must not be DISCONTINUED (otherwise BusinessRuleException → 422)
  • Product stock must be ≥ requested quantity (otherwise BusinessRuleException → 422)

These checks happen after locking. Without the lock, another transaction could decrement stock or discontinue the product between request arrival and validation.

DB 5. Persist & Outbox

If all validations pass:

  1. Stock decrement: each product's stock is reduced by the ordered quantity
  2. Price snapshot: the current product price is captured on each OrderLine — prices are not live references
  3. Total computed: sum of (quantity × unit price) for all lines
  4. Order saved: orderRepository.save(order) cascades to order lines (CascadeType.ALL)
  5. Outbox event: outboxPublisher.publish(new DomainEvent.OrderPlaced(...)) inserts a CloudEvents-formatted row into outbox_events — in the same transaction
Why same-transaction outbox? If the commit succeeds, both the order and the event are durable. If it fails, neither exists. This eliminates the dual-write problem. See Outbox Pattern for the full design rationale.

HTTP 6. Response

Back in the controller, the OrderResponse record is wrapped in a 201 Created response with a Location: /api/orders/{id} header. Jackson 3 serializes the record to JSON.

On any exception, ExceptionTranslator catches it, returns RFC 9457 Problem Details, and the @Transactional proxy rolls back.

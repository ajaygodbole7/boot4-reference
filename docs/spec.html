Boot4 Reference API Specification

REST API built with Spring Boot 4.0 / Java 25. All responses use application/json. Errors follow RFC 9457 Problem Details.

Base URL: http://localhost:8080
Management: http://localhost:8081 (health, metrics, prometheus)

Conventions

  • IDs are TSID-based Long values (e.g. 553726781652992).
  • Timestamps are ISO-8601 UTC (Instant).
  • Prices use BigDecimal with up to 4 decimal places.
  • Status transitions are explicit via POST .../status endpoints.
  • Keyset pagination uses afterCreatedAt + afterId cursors.
  • Optimistic locking: stale writes return 409.

Error Handling

All errors return RFC 9457 Problem Details:

{
  "type": "https://api.boot4ref.example.com/errors/404",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "Product not found with id: 123",
  "instance": "/api/products/123",
  "errorCode": "RESOURCE_NOT_FOUND",
  "timestamp": "2026-03-01T12:00:00Z",
  "request": {
    "httpMethod": "GET",
    "requestPath": "/api/products/123"
  }
}

In the dev profile, error responses include exception class name and stackTrace.

PUT /api/products/{id}

Full replacement of a product's mutable fields. Does not change status.

Request Body

Content-Type: application/json

{
  "name": "Updated Keyboard",         // required, 3-100 chars
  "description": "New description",    // optional, max 500 chars
  "price": 159.99,                     // required, positive
  "stock": 50                          // required, >= 0
}

Responses

200 — ProductResponse

400 — Validation error

404 — Product not found

409 — Optimistic lock conflict (stale version)

PATCH /api/products/{id}

Partial update. Only non-null fields in the request body are applied; omitted fields are unchanged. Setting a field to null (to clear it) is not supported — the record-based DTO cannot distinguish absent fields from explicit nulls.

Request Body

Content-Type: application/json

{
  "price": 139.99,    // only update price
  "stock": 100        // and stock
}

Responses

200 — ProductResponse

404 — Product not found

409 — Optimistic lock conflict

415 — Wrong Content-Type (must be application/json)

DELETE /api/products/{id}

Hard-delete a product.

Responses

204 — No content

404 — Product not found

Orders

POST /api/orders

Create a new order. Acquires pessimistic locks on products (sorted by PK to prevent deadlocks), validates stock and product status, snapshots prices, and computes the total.

Headers

NameRequiredDescription
Idempotency-KeyRecommendedUnique key for at-most-once creation. If a matching order exists, it is returned.

Request Body

Content-Type: application/json

{
  "items": [
    { "productId": 553726781652992, "quantity": 2 },
    { "productId": 553726781652993, "quantity": 1 }
  ]
}

Validation Rules

  • items must not be empty
  • productId is required (not null)
  • quantity is required and must be positive

Business Rules

  • Product must exist and not be DISCONTINUED — otherwise 422
  • Product stock must be sufficient — otherwise 422
  • Price is snapshotted at order time (not a live reference)
  • Stock is decremented atomically under pessimistic lock

Responses

201 — OrderResponse + Location header

400 — Validation error

404 — Product not found

409 — Duplicate idempotency key (returns original order)

422 — Discontinued product or insufficient stock

GET /api/orders/{id}

POST /api/orders/{id}/status

Transition an order's lifecycle status. See lifecycle rules.

Request Body

{
  "status": "CONFIRMED"
}

Business Rules

  • Cancellation (CANCELLED) restores stock to all referenced products
  • Stock restoration uses pessimistic locking (sorted by PK)

Responses

200 — OrderResponse

404 — Order not found

409 — Invalid status transition

Order Lifecycle

                ┌──→ CANCELLED
                │
  PLACED ──→ CONFIRMED ──→ SHIPPED ──→ DELIVERED
    │                         │
    └──→ CANCELLED            └──→ (terminal)
FromToDescription
PLACED→ CONFIRMEDSeller confirms the order
PLACED→ CANCELLEDBuyer cancels (stock restored)
CONFIRMED→ SHIPPEDOrder ships
CONFIRMED→ CANCELLEDSeller cancels (stock restored)
SHIPPED→ DELIVEREDDelivery confirmed

All other transitions are rejected with 409 Conflict. DELIVERED and CANCELLED are terminal states.

Keyset Pagination

This API uses keyset (cursor-based) pagination instead of offset pagination. This avoids the performance degradation of OFFSET on large tables and provides stable results when data changes.

How to paginate

  1. Request the first page: GET /api/products?limit=20
  2. Take the createdAt and id of the last item in the response
  3. Request the next page: GET /api/products?afterCreatedAt={lastCreatedAt}&afterId={lastId}&limit=20
  4. Repeat until the response is empty or has fewer items than limit

Idempotency

Order creation supports idempotency via the Idempotency-Key header.

  • If an order with the given key already exists, the original order is returned (no duplicate created)
  • The key is stored in the idempotency_key column (unique constraint)
  • Clients should generate a UUID for each unique order intent

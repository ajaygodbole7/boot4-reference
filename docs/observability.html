Observability

Logs, traces, metrics — OpenTelemetry to Grafana.

Key Points

  • Three pillars: logs (Loki), traces (Tempo), metrics (Prometheus) — all accessible from Grafana at localhost:3000
  • OpenTelemetry Collector receives all three OTLP signals — traces → Tempo, metrics → Prometheus exporter, logs → Loki
  • Structured logging uses ECS JSON format when STRUCTURED_LOGGING=true (in Docker); default console format for local dev
  • MDC correlation IDs (traceId, spanId) in every log line — click through to traces in Tempo
  • Actuator exposes /actuator/prometheus on management port 8081 — separate from the API port

Deep Dive: Structured Logging

Configuration

File: src/main/resources/application.properties

Logging format is controlled by the STRUCTURED_LOGGING environment variable:

EnvironmentFormatConfiguration
Local developmentSpring Boot default (human-readable)No special config needed
Docker / productionECS JSON (machine-parseable)STRUCTURED_LOGGING=true activates logging.structured.format.console=ecs

ECS Format

With structured logging active, every log line is an ECS (Elastic Common Schema) JSON object. Loki, Elasticsearch, and most log aggregators parse it natively:

{
  "@timestamp": "2026-03-01T16:03:32.868Z",
  "log.level": "INFO",
  "message": "Created order id=815977570206793968",
  "ecs.version": "1.2.0",
  "service.name": "boot4-reference",
  "process.thread.name": "http-nio-8080-exec-1",
  "log.logger": "com.example.boot4ref.order.service.OrderService",
  "trace.id": "abc123def456...",
  "span.id": "789ghi..."
}

Log Levels

LevelUsage in codebase
ERRORUnhandled exceptions (5xx), outbox publish failures after retries exhausted
WARNClient errors (4xx), recoverable failures, invalid status transitions
INFORequest handling, order creation, status transitions, outbox processing
DEBUGDetailed operation logs (product updates, query parameters, lock acquisition)

Deep Dive: Distributed Tracing

How traces are exported

Spring Boot 4 has built-in OTLP trace export via Micrometer Tracing + OpenTelemetry:

# application.properties
management.otlp.tracing.endpoint=http://localhost:4318/v1/traces

Spring auto-instruments these automatically:

  • Incoming HTTP requests (DispatcherServlet)
  • JDBC calls (datasource instrumentation)
  • Kafka sends (template instrumentation)
  • Scheduled tasks (@Scheduled outbox poller)

OTel Collector

File: infra/otel-collector.yml

The collector receives OTLP data over HTTP (port 4318) and routes each signal to its backend:

  • Traces → Tempo — full traces for distributed trace visualization
  • Metrics → Prometheus exporter — OTLP metrics re-exported in Prometheus format on :8889, scraped by Prometheus
  • Logs → Loki — forwarded via OTLP/HTTP to loki:3100/otlp

Actuator Endpoints

Management endpoints run on a separate port (8081) to keep them off the public API port:

Key Metrics

MetricTypeWhat it measures
http.server.requestsTimerRequest latency by URI, method, status (with percentile histograms)
hikaricp.connections.activeGaugeActive database connections

Percentile histograms are enabled for HTTP request latency:

management.metrics.distribution.percentiles-histogram.http.server.requests=true

Grafana computes p50, p95, p99 latencies from these histogram buckets.

Deep Dive: Correlation IDs

Every log line includes traceId and spanId via MDC (Mapped Diagnostic Context):

logging.pattern.correlation=[${spring.application.name:},%X{traceId:-},%X{spanId:-}]

Debugging workflow:

  1. An error appears in Loki: "Product not found" traceId=abc123
  2. Copy abc123, paste into Tempo's search
  3. See the full trace: which HTTP request, which DB queries, how long each took
  4. Identify whether the problem is the client (bad ID), the database (missing row), or the application (logic error)
Why separate management port? Actuator on a separate port (8081) because:
  • Not exposed through the public load balancer
  • Prometheus scrapes directly — no API gateway auth
  • Health checks don't pollute API access logs

Grafana Dashboards

Dashboards are auto-provisioned from infra/grafana/dashboards/ and connect to all three datasources (configured in infra/datasources.yaml).

infra/start.sh launches Grafana at http://localhost:3000 with:

  • Pre-configured datasources for Tempo, Loki, and Prometheus
  • Pre-loaded dashboards for application metrics, JVM stats, and request tracing
  • No login required (anonymous access enabled for local development)

Prometheus Scrape Config

File: infra/prometheus.yml

Prometheus scrapes two targets every 10 seconds:

  • otel-collector:8889/metrics — OTLP metrics from the app, re-exported in Prometheus format
  • host.docker.internal:8081/actuator/prometheus — application metrics from Spring Actuator
